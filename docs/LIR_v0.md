# APL Normalized Lower IR (LIR)

Status: **Compiler IR 0.1**

APL LIR is a deterministic compiler-facing representation derived from a verified semantic APL program. It is not a replacement source language and does not define new program meaning.

The normative execution semantics remain those of the source APL draft. A backend consuming LIR must preserve those semantics.

## 1. Pipeline role

```text
canonical semantic APL IR
        |
        v
     verifier
        |
        v
 deterministic lowering
        |
        v
 normalized APL LIR 0.1
        |
        +--> LIR verifier
        |
        +--> optimizer
        |
        +--> WASM/native backend
```

The source verifier runs before lowering. The LIR verifier is also capable of checking a serialized LIR artifact without access to the source program.

## 2. Root object

A LIR 0.1 module contains exactly:

```json
{
  "apl_lir": "0.1",
  "source_apl": "0.0.14",
  "module": "example",
  "entry": "main",
  "runtime": {
    "capability_grants_required": true,
    "capabilities": [],
    "limits": {
      "steps": 100,
      "output_lines": 0,
      "host_reads": 0
    }
  },
  "functions": []
}
```

- `source_apl` identifies the semantic language version that was lowered.
- `capability_grants_required` is false before source APL 0.0.8 and true from 0.0.8 onward.
- Before source APL 0.0.10, all three runtime limits are `null`.
- From source APL 0.0.10 onward, limits are the exact verified source limits.
- `capabilities` is the sorted exact union of inferred transitive function effects.

## 3. Deterministic normalization

Lowering is deterministic.

For a given semantic program:

- functions are serialized lexicographically by function name;
- source SSA names are discarded;
- function/block SSA values are renamed densely as `v0`, `v1`, ...;
- basic blocks are named densely as `b0`, `b1`, ... in construction order;
- record constructor fields are serialized lexicographically;
- branch joins use explicit block parameters rather than implicit phi nodes;
- semantic source `if`, `repeat`, `yield`, contracts, and invariant declarations do not survive as high-level control constructs.

Alpha-renaming source parameters or SSA ids does not change normalized LIR.

Reordering source functions does not change normalized LIR.

## 4. Function form

A function contains exactly:

```json
{
  "name": "f",
  "params": [
    {"id": "v0", "type": "i64"}
  ],
  "returns": "i64",
  "effects": [],
  "blocks": []
}
```

Function parameter names are erased; only positional ids and types remain.

The `effects` list is a sorted exact transitive effect set reconstructed from LIR operations and calls. LIR 0.1 recognizes:

- `console.write`
- `fs.read_text`
- `net.get_text`

The LIR call graph must remain acyclic.

## 5. Basic blocks and block parameters

Each block contains exactly:

```json
{
  "id": "b0",
  "params": [],
  "ops": [],
  "term": {"op": "return", "value": "v0"}
}
```

The entry block is always `b0` and has no block parameters.

Every non-entry data-flow join is expressed through typed block parameters. Branch edges carry an ordered argument list whose arity and types must exactly match the destination block parameter list.

This is the LIR equivalent of SSA phi semantics, but the transfer is explicit in the CFG.

## 6. Terminators

LIR 0.1 terminators are:

- `br`
- `cond_br`
- `return`
- `trap`

Example:

```json
{
  "op": "cond_br",
  "cond": "v3",
  "then": {"target": "b1", "args": ["v0", "v1"]},
  "else": {"target": "b2", "args": ["v0", "v1"]}
}
```

A terminator is the final control transfer of a block.

`cond_br` is legal only when the source version supports structured branching (APL 0.0.2+).

`trap` is legal only for source APL 0.0.7+ and preserves the verified source trap code, message, and semantic source location.

## 7. Step accounting

Every semantic source instruction or predicate node that consumes one APL step is lowered to an explicit:

```json
{"op":"budget.step","where":"main[2]"}
```

Internal compiler operations used only to express CFG mechanics do not consume semantic APL steps.

Examples of internal operations that are not independently charged include:

- CFG branch transfer;
- loop header comparison generated by lowering;
- loop-index increment generated by lowering;
- block-parameter transfer.

This explicit separation is required so compiled execution can reproduce interpreter resource-limit ordering.

## 8. Structured `if` lowering

A semantic value-producing `if` lowers to:

1. one `cond_br`;
2. explicit then/else blocks;
3. one merge block;
4. a merge block parameter carrying the selected yielded value.

No semantic `if` or `yield` operation remains in LIR.

A branch that traps does not need to reach the merge block.

## 9. Bounded `repeat` lowering

A semantic `repeat` lowers to:

1. the source instruction's `budget.step`;
2. `repeat.guard` for negative-count / declared-maximum enforcement;
3. an explicit loop header with index and carried-value block parameters;
4. a body block;
5. a back-edge carrying the incremented index and yielded carry;
6. an exit block carrying the final value.

The generated index initialization, comparison, and increment are compiler mechanics and do not add source steps.

Nested structured control must always use the current block-local loop-index value on the back-edge.

## 10. Contracts and reusable invariants

Draft 0.0.11+ contracts and Draft 0.0.14 invariants are lowered into ordinary pure predicate operations plus:

```json
{
  "op": "guard",
  "cond": "v7",
  "code": "apl.precondition_failed",
  "message": "contract 'positive' failed: value must be positive",
  "where": "f.requires[0]"
}
```

Normalized guard codes are limited to:

- `apl.precondition_failed`
- `apl.postcondition_failed`
- `apl.invariant_failed`

Invariant references are inlined into their verified pure predicate bodies. No recursive invariant graph exists in Draft 0.0.14.

## 11. Value operations

LIR uses explicit operation families including:

- `const`
- `i64.add/sub/mul/div/rem`
- `i64.lt/le/gt/ge`
- `value.eq/lt/le/gt/ge`
- `bool.not/and/or`
- `array.make/get/len`
- `record.make/get`
- `range.check/value`
- `quantity.attach/value/add/sub/mul/div`
- `call`
- `console.write`
- `host.fs.read_text`
- `host.net.get_text`
- `guard`
- `repeat.guard`
- `budget.step`

Operations that may produce a semantic runtime trap carry the original semantic `where` location needed for stable diagnostics.

Feature operations are rejected if `source_apl` predates the semantic APL draft that introduced them.

## 12. LIR verification

`verify_lir` checks, independently of source text:

- root and function schemas;
- source APL compatibility;
- dense canonical block/value ids;
- type correctness;
- block-local SSA availability;
- branch target existence;
- branch arity/type equality;
- function call signatures;
- acyclic call graph;
- exact transitive function effects;
- exact module capabilities;
- version-dependent runtime metadata;
- operation feature gates;
- canonical guard semantics;
- return types.

A modified LIR artifact that violates those constraints is rejected before backend compilation.

## 13. Canonical encoding and identity

LIR uses the repository's canonical JSON encoding:

- UTF-8;
- recursively sorted object keys;
- no insignificant whitespace;
- JSON arrays preserved in their normalized semantic order.

`apl lower-hash` returns SHA-256 over that canonical normalized LIR.

The lower hash is a compiler-artifact identity. It is distinct from the semantic source hash.

## 14. CLI

```text
apl lower program.apl
apl lower-hash program.apl
apl verify-lir program.lir.json
```

`apl lower` verifies source APL before lowering and emits canonical LIR JSON.

`apl verify-lir` verifies a serialized normalized LIR artifact without requiring the original source program.

## 15. Deliberate exclusions from LIR 0.1

LIR 0.1 does not yet define:

- WASM encoding;
- native ABI;
- memory layout optimization;
- instruction selection;
- optimization passes;
- equivalence certificates;
- binary serialization;
- debug/source-map compression.

Those are subsequent M4 layers built on this normalized CFG contract.
